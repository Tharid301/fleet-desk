# วิธีแก้ฐานข้อมูลเมื่อเว็บเปลี่ยน (Migration)

## คำตอบสั้นๆ: แก้ได้ครับ แต่**ห้ามแก้ไฟล์ `01_schema.sql` เดิม**

---

## ทำไมห้ามแก้ไฟล์เดิม

`01_schema.sql` รันไปแล้วครั้งเดียว ตารางถูกสร้างไปแล้ว

ถ้าคุณกลับไปแก้ไฟล์นั้นแล้วรันใหม่:
- คำสั่ง `create table if not exists` จะเห็นว่าตารางมีอยู่แล้ว → **ข้ามไปเฉยๆ ไม่แก้อะไร**
- คุณจะนึกว่าแก้แล้ว แต่ฐานข้อมูลจริงยังเหมือนเดิม
- แล้วมาปวดหัวทีหลังว่าทำไมโค้ดกับฐานข้อมูลไม่ตรงกัน

**วิธีที่ถูก: เขียนไฟล์ใหม่ต่อท้าย** `02_xxx.sql`, `03_xxx.sql` ไปเรื่อยๆ
แต่ละไฟล์บอกว่า "เปลี่ยนจากสถานะก่อนหน้าเป็นสถานะใหม่ยังไง"

```
supabase/
├── 01_schema.sql              ← รันแล้ว ห้ามแตะ
├── 02_add_fuel_log.sql        ← เพิ่มทีหลัง
├── 03_add_customer_rating.sql ← เพิ่มทีหลังอีก
└── MIGRATION-GUIDE.md         ← ไฟล์นี้
```

เปรียบเทียบ: เหมือนสมุดบัญชี — เขียนรายการใหม่ต่อท้าย ไม่ใช่ไปลบบรรทัดเก่าแล้วเขียนทับ

---

## แบ่งการเปลี่ยนแปลงเป็น 3 ระดับ

### 🟢 ระดับปลอดภัย — ทำได้เลย ข้อมูลเดิมไม่กระทบ

| ทำอะไร | ตัวอย่างคำสั่ง |
|---|---|
| เพิ่มคอลัมน์ใหม่ | `alter table vehicles add column if not exists nickname text;` |
| เพิ่มตารางใหม่ | `create table if not exists fuel_logs (...);` |
| เพิ่ม index | `create index if not exists ... ;` |
| เพิ่มหมวดหมู่ | `insert into expense_categories ... on conflict do nothing;` |

**เคล็ดลับ:** คอลัมน์ใหม่ต้องยอมให้ว่างได้ (`null`) หรือมีค่าเริ่มต้น
ถ้าบังคับ `not null` โดยไม่มีค่าเริ่มต้น → แถวเก่าที่มีอยู่จะทำให้คำสั่งล้มเหลว

```sql
-- ❌ พัง ถ้ามีข้อมูลเดิมอยู่แล้ว
alter table vehicles add column color_code text not null;

-- ✅ ถูก
alter table vehicles add column color_code text not null default '';
```

### 🟡 ระดับต้องระวัง — สำรองข้อมูลก่อน

| ทำอะไร | ความเสี่ยง |
|---|---|
| เปลี่ยนชนิดข้อมูล | ข้อมูลเดิมอาจแปลงไม่ได้ |
| เปลี่ยนชื่อคอลัมน์ | โค้ดเว็บที่ยังใช้ชื่อเก่าจะพัง |
| เพิ่มเงื่อนไขบังคับ | ข้อมูลเดิมที่ไม่ผ่านเงื่อนไขจะทำให้ล้มเหลว |

**วิธีเปลี่ยนชื่อคอลัมน์แบบไม่ให้เว็บล่ม** (ทำ 3 ขั้น คนละวัน):
1. เพิ่มคอลัมน์ใหม่ + ก๊อปข้อมูลจากคอลัมน์เก่า (เว็บยังใช้ชื่อเก่าได้)
2. แก้เว็บให้ใช้ชื่อใหม่ → deploy → ดูว่าไม่มีปัญหา
3. ค่อยลบคอลัมน์เก่า

### 🔴 ระดับอันตราย — ข้อมูลหายถาวร

| ทำอะไร | ผล |
|---|---|
| `drop column` | ข้อมูลในคอลัมน์นั้นหายหมด กู้ไม่ได้ |
| `drop table` | ทั้งตารางหาย |
| `delete` ไม่ใส่ `where` | ลบทุกแถว |
| `truncate` | ล้างตารางทั้งหมด |

**กฎเหล็ก:** ก่อนรันคำสั่งกลุ่มนี้ **ต้องสำรองข้อมูลและลองกู้คืนจริง** ไม่ใช่แค่กดสำรองแล้วเชื่อว่าได้

## ขั้นตอนที่ควรทำทุกครั้ง

```
1. สำรองข้อมูล        Supabase → Database → Backups → Download
2. อ่านคำสั่งให้เข้าใจ  ถามผู้พัฒนาว่าคำสั่งนี้ทำอะไร เสี่ยงมั้ย
3. ลองในสนามซ้อม      สร้างโปรเจกต์ Supabase อีกอันไว้ทดลอง
4. รันในของจริง        SQL Editor → วาง → Run
5. ตรวจผล             เปิดเว็บ ลองใช้จริง ดูว่าข้อมูลเดิมยังอยู่ครบ
6. commit ลง git      เก็บไฟล์ .sql ไว้เป็นประวัติ
```

**ข้อ 3 สำคัญที่สุด** — Supabase สร้างโปรเจกต์ได้หลายอันฟรี ควรมี 2 อัน:
- `fleet-desk-dev` — สนามซ้อม ข้อมูลปลอม พังได้
- `fleet-desk-prod` — ของจริง ข้อมูลลูกค้า ห้ามทดลอง

## ตัวอย่างจริง: ถ้าอยากเพิ่มระบบบันทึกการเติมน้ำมัน

สมมติวันหนึ่งอยากบันทึกทุกครั้งที่เติมน้ำมัน เพื่อดูว่ารถคันไหนกินน้ำมันผิดปกติ

**สร้างไฟล์ `02_add_fuel_log.sql`:**

```sql
-- เพิ่มตารางบันทึกการเติมน้ำมัน
-- วันที่: 19 ก.ย. 2569
-- เหตุผล: ต้องการดูอัตราสิ้นเปลืองรายคัน เพื่อจับรถที่มีปัญหาเครื่องยนต์

create table if not exists fuel_logs (
  id          uuid primary key default gen_random_uuid(),
  vehicle_id  uuid not null references vehicles(id) on delete cascade,
  booking_id  uuid references bookings(id),
  filled_on   date not null default current_date,
  liters      numeric(8,2) not null,
  amount      numeric(12,2) not null,
  odometer    integer,
  station     text,
  receipt_url text,
  created_by  uuid references profiles(id),
  created_at  timestamptz not null default now(),

  constraint fuel_positive check (liters > 0 and amount > 0)
);

create index if not exists idx_fuel_vehicle on fuel_logs(vehicle_id, filled_on);

-- อย่าลืมเปิด RLS ทุกตารางใหม่ ไม่งั้นใครก็อ่านได้
alter table fuel_logs enable row level security;

drop policy if exists fuel_access on fuel_logs;
create policy fuel_access on fuel_logs for all
  using (is_staff_or_owner()) with check (is_staff_or_owner());
```

จากนั้นบอกผู้พัฒนาให้เพิ่มหน้าจอบันทึกน้ำมันในเว็บ

## ข้อผิดพลาดที่พบบ่อย

| พลาด | ผล | ป้องกัน |
|---|---|---|
| ลืมเปิด RLS ตารางใหม่ | ใครก็อ่านข้อมูลได้ | ทุกตารางใหม่ต้อง `enable row level security` |
| เพิ่มคอลัมน์ `not null` ไม่มี default | คำสั่งล้มเหลว | ใส่ `default` เสมอ |
| แก้ฐานข้อมูลแต่ไม่แก้เว็บ | เว็บพังเพราะหาคอลัมน์ไม่เจอ | แก้ทั้งสองฝั่งพร้อมกัน |
| ไม่สำรองก่อน `drop` | ข้อมูลหายถาวร | สำรอง **และลองกู้คืน** ก่อน |
| ทดลองในของจริง | ข้อมูลลูกค้าเสียหาย | มีสนามซ้อมแยก |
| ไม่เก็บไฟล์ .sql ลง git | ไม่รู้ว่าเคยแก้อะไรไปบ้าง | commit ทุกไฟล์ migration |

## สรุป

| คำถาม | คำตอบ |
|---|---|
| แก้ฐานข้อมูลทีหลังได้มั้ย | **ได้ ตลอดเวลา** |
| แก้ไฟล์ `01_schema.sql` เดิมได้มั้ย | **ไม่ได้** — เขียนไฟล์ใหม่ต่อท้าย |
| ข้อมูลเดิมหายมั้ย | ไม่หาย ถ้าเป็นการเพิ่ม · หายถ้าเป็นการลบ |
| ต้องปิดเว็บตอนแก้มั้ย | การเพิ่มไม่ต้อง · การเปลี่ยนโครงสร้างใหญ่ควรปิดสั้นๆ |
| ใครรันคำสั่ง | คุณเอง (ก๊อปวางใน Supabase) หรือผู้พัฒนา |
