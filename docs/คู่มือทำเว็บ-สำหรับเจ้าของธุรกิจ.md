# คู่มือทำเว็บสำหรับเจ้าของธุรกิจ

เขียนสำหรับคนที่ไม่เขียนโค้ดเอง แต่ต้องตัดสินใจและตรวจงานได้
อ้างอิงจากประสบการณ์จริงในโปรเจกต์ Fleet Desk

## ส่วนที่ 1 — เว็บหนึ่งเว็บประกอบด้วยอะไร

เปรียบเทียบกับร้านอาหาร:

| ส่วน | เปรียบเป็น | หน้าที่ | สถานะโปรเจกต์เรา |
|---|---|---|---|
| **Frontend** (หน้าบ้าน) | หน้าร้าน โต๊ะ เมนู | สิ่งที่ผู้ใช้เห็นและกด | ✅ มีแล้ว |
| **Backend** (หลังบ้าน) | ครัว + พนักงาน | รับคำสั่ง ตรวจสิทธิ์ ตัดสินใจ | ❌ ยังไม่มี |
| **Database** (คลังเก็บของ) | ห้องเก็บของ + สมุดบัญชี | เก็บข้อมูลถาวร | ❌ ยังไม่มี |

### สำคัญมาก: "เว็บอยู่บนอินเทอร์เน็ต" ≠ "ข้อมูลอยู่บนอินเทอร์เน็ต"

ตอนนี้ตัวเว็บอยู่บนเน็ตจริง ใครมีลิงก์ก็เปิดได้
แต่ข้อมูลที่กรอกถูกเก็บไว้ใน **เบราว์เซอร์ของเครื่องที่กรอก** เท่านั้น

เหมือนไปนั่งร้านอาหาร แล้วจดออเดอร์ใส่สมุดตัวเอง เก็บใส่กระเป๋ากลับบ้าน — ร้านไม่รู้เรื่องเลย

ผลที่ตามมา:
- เปิดจากมือถือกับคอม เห็นข้อมูลคนละชุด
- พนักงานเปิดจากเครื่องตัวเอง ไม่เห็นข้อมูลที่เจ้าของกรอก
- ล้างแคชเบราว์เซอร์ = ข้อมูลหาย

## ส่วนที่ 3 — สามเรื่องที่มือใหม่มักไม่รู้

### 3.1 แยกสนามซ้อมกับสนามจริง (Staging vs Production)

**ปัญหา:** ทดลองแก้บนข้อมูลลูกค้าจริง พอพังคือข้อมูลจริงเสียหาย

**ตัวอย่างจากระบบเรา:** อยากเปลี่ยนสูตรคิดค่าเช่าจากปัดขึ้น 3 ชม. เป็น 4 ชม.
- ไม่มีสนามซ้อม → สูตรผิด → ใบเสร็จวันนั้นผิดหมด → ต้องโทรขอโทษลูกค้าทีละราย
- มีสนามซ้อม → ลองจอง 10 แบบด้วยข้อมูลปลอม ดูว่าคิดเงินถูก แล้วค่อยย้ายมาจริง

**เปรียบเทียบ:** เชฟคิดเมนูใหม่ ต้องลองทำในครัวก่อน ไม่ใช่ทดลองสูตรกับจานที่กำลังเสิร์ฟ

### 3.2 ความปลอดภัยต้องอยู่ที่หลังบ้านเสมอ

**หน้าบ้านกันไม่ได้** เพราะโค้ดหน้าบ้านถูกส่งไปรันในเครื่องของผู้ใช้ เขาเป็นเจ้าของเครื่อง เขาแก้ได้

**ตัวอย่าง:** ระบบซ่อนปุ่มแก้ไขไม่ให้นักบัญชีเห็น
→ คนที่รู้วิธี กดขวา → Inspect → ลบคำสั่งซ่อน → ปุ่มโผล่ → แก้ได้

**เปรียบเทียบ:** ติดป้าย "ห้ามเข้า" หน้าห้องแต่ไม่ล็อกประตู — กันคนสุภาพได้ กันคนตั้งใจไม่ได้

**วิธีที่ถูก:** หลังบ้านตรวจทุกคำสั่งว่า "คนส่งมีสิทธิ์มั้ย" ส่วนการซ่อนปุ่มยังทำ แต่เพื่อความสวยงาม ไม่ใช่ความปลอดภัย

**เรื่องรหัสลับ:** รหัสเชื่อมฐานข้อมูลมี 2 แบบ
- แบบเปิดเผยได้ (anon key) — ใส่ในหน้าบ้านได้
- แบบห้ามเปิดเผย (service key) — **ห้ามใส่ในหน้าบ้านเด็ดขาด** เท่ากับยกกุญแจให้คนทั้งโลก

### 3.3 Git — ปุ่มเซฟที่ย้อนกลับได้

**เคสจริงที่เกิดในโปรเจกต์นี้:** ลืมประกาศตัวแปร 1 ตัว → ทั้งแอปหน้าขาว
- ไม่มี Git → เดาผิด 1 รอบ ใส่ตัวดักจับ error รอบถัดไปถึงเจอ = **2 รอบบทสนทนา**
- มี Git → "เมื่อวานยังใช้ได้" → เทียบว่าแก้อะไรไป → **เจอใน 1 นาที** หรือย้อนกลับใน 10 วินาที

## ส่วนที่ 4 — ข้อผิดพลาดที่พบบ่อย

| พลาด | ผลที่ตามมา | ป้องกัน |

| เชื่อว่าหน้าบ้านกันได้ | โดนข้ามสิทธิ์ | กฎต้องอยู่หลังบ้าน |

## ส่วนที่ 5 — วิธีตรวจงานคนเขียนโค้ด (หรือ AI)

### คำถาม 3 ข้อที่ทรงพลังที่สุด

**1. "อันนี้ทดสอบยังไง"**
ถ้าตอบว่า "คอมไพล์ผ่าน" = **ยังไม่ได้ทดสอบ** แค่แปลว่าไวยากรณ์ถูก
โปรแกรมที่ไวยากรณ์ถูกแต่รันแล้วพังทันทีมีอยู่จริง (เกิดกับเราแล้ว)

**2. "ทดสอบด้วยของจริงหรือของปลอม"**
เคสจริง: AI เขียนเทสต์ที่กำหนดค่าตัวแปรขึ้นมาเอง เทสต์เลยผ่าน ทั้งที่แอปจริงไม่มีค่านั้น → แอปพังสนิทแต่เทสต์เขียว

**3. "อะไรที่ยังไม่ได้ตรวจ"**
บังคับให้แยกระหว่าง "ยืนยันแล้ว" กับ "เดา"

### สัญญาณอันตรายในคำตอบ

- บอกว่า "เสร็จแล้ว" แต่ไม่บอกว่าทดสอบยังไง
- อธิบายยาวแต่ไม่มีตัวเลข/ผลลัพธ์จริง
- **เปลี่ยนคำอธิบายสาเหตุไปมา** = ยังเดาอยู่ (เกิดขึ้นจริงตอนแก้ปัญหาเลื่อนหน้าจอ เดาผิด 3 รอบ)
- ใช้คำว่า "น่าจะ" "ควรจะ" แทน "ตรวจแล้วพบว่า"

### วิธีตรวจที่ได้ผลที่สุด

**ลองใช้แบบคนใช้จริง ไม่ใช่แค่ดูว่าหน้าจอขึ้น**

บั๊กร้ายแรง 3 ตัวในโปรเจกต์นี้ เจ้าของธุรกิจเป็นคนเจอทั้งหมด:

| บั๊ก | เจอได้ยังไง | ทำไมเครื่องมือจับไม่ได้ |
|---|---|---|
| ฟอร์มพิมพ์ได้ตัวเดียว | ลองพิมพ์จริง | ฟอร์มแสดงผลถูกต้อง โค้ดไม่ผิดไวยากรณ์ |
| ข้อมูลลูกค้ารั่ว | **ดูในมุมลูกค้า** แล้วถามว่าควรเห็นมั้ย | ไม่ใช่ error เป็นการตัดสินใจผิด |
| หน้าขาวบนมือถือ | เปิดบนอุปกรณ์จริงหลายเครื่อง | เป็น runtime error ที่คอมไพเลอร์มองไม่เห็น |

**เทคนิคเพิ่มเติม:** ลอง**ทางที่ผิด**ด้วย — กรอกไม่ครบแล้วกดส่ง, ใส่เลขติดลบ, กดปุ่มรัวๆ, ใส่ทศนิยม 5 ตำแหน่ง

## ส่วนที่ 6 — Git

### คืออะไร
ปุ่มเซฟในเกมที่เซฟได้ไม่จำกัดจุด และย้อนกลับไปจุดไหนก็ได้

| ศัพท์ | แปลว่า |
|---|---|
| **repository (repo)** | โฟลเดอร์โปรเจกต์ที่ Git ดูแลอยู่ |
| **commit** | กดเซฟ 1 ครั้ง พร้อมโน้ตว่าแก้อะไร |
| **history / log** | รายการเซฟทั้งหมด |
| **diff** | เทียบว่า 2 เวอร์ชันต่างกันตรงไหน |
| **revert** | ย้อนกลับไปจุดเซฟก่อนหน้า |
| **branch** | แตกไปทดลองแยก ไม่กระทบของหลัก |
| **merge** | รวมสิ่งที่ทดลองกลับเข้าของหลัก |
| **push / pull** | ส่งขึ้น / ดึงลง จากคลาวด์ |
| **GitHub** | บริการเก็บ repo บนคลาวด์ (ฟรี) |

### คำสั่งที่ใช้จริง 90% ของเวลา

```bash
git status                  # ดูว่าแก้อะไรไปบ้าง ยังไม่ได้เซฟ
git add -A                  # เตรียมไฟล์ที่แก้ทั้งหมด
git commit -m "ข้อความ"      # เซฟ พร้อมโน้ต
git log --oneline           # ดูประวัติเซฟทั้งหมด
git diff                    # ดูว่าแก้อะไรไปบ้างเทียบกับเซฟล่าสุด
git revert <รหัส commit>     # ย้อนกลับการแก้ครั้งนั้น
git push                    # ส่งขึ้น GitHub
```

### เขียนข้อความ commit ยังไงให้มีประโยชน์

| ❌ ไม่ดี | ✅ ดี |
|---|---|
| "update" | "แก้บั๊กฟอร์มพิมพ์ได้ตัวเดียว (ย้าย Field ออกจาก component body)" |
| "fix bug" | "เพิ่มช่วงเคลียรถ 1 ชม. หลังคืนรถ กันจองทับ" |
| "เพิ่มโค้ด" | "ตัดข้อมูลลูกค้าออกจากหน้าสาธารณะ (PDPA)" |

**หลักคิด:** เขียนให้ตัวเองในอีก 6 เดือนอ่านแล้วเข้าใจว่าทำไมถึงแก้

## ส่วนที่ 7 — ฐานข้อมูล

### ต่างจาก Excel ยังไง

| | Excel | ฐานข้อมูล |
|---|---|---|
| หลายคนแก้พร้อมกัน | ทับกัน | จัดคิวให้ ไม่ทับ |
| ป้องกันข้อมูลผิด | ไม่ได้ | บังคับได้ เช่น "เบอร์โทรห้ามว่าง" |
| ค้นข้อมูลแสนแถว | ค้าง | เร็วมาก |
| กันจองซ้ำ | ไม่ได้ | **ได้** |
| ย้อนดูว่าใครแก้อะไร | ยาก | ทำได้ |

### แนวคิดสำคัญ 3 อย่าง

**1. ตาราง (Table)** — แต่ละเรื่องอยู่คนละตาราง
ตารางรถ / ตารางลูกค้า / ตารางการจอง แทนที่จะยัดรวมแผ่นเดียว

**2. การเชื่อมโยง (Relationship)** — ไม่เก็บข้อมูลซ้ำ
ตารางการจองเก็บแค่ "รหัสลูกค้า" แล้วชี้ไปตารางลูกค้า
→ ลูกค้าเปลี่ยนเบอร์โทร แก้ที่เดียว ทุกการจองอัปเดตตาม

**3. ธุรกรรม (Transaction)** — กลุ่มคำสั่งที่ต้องสำเร็จพร้อมกัน
ถ้ามีอันใดพัง ยกเลิกทั้งชุด
**นี่คือสิ่งที่แก้ปัญหาจองซ้ำ** — ลูกค้า A กด 18:00 ลูกค้า B กด 18:10 ฐานข้อมูลจะปฏิเสธคนที่สองทันที ไม่ใช่รอบริษัทมาเช็คตอน 19:00

### คืออะไร
ชุดสำเร็จที่รวมทุกอย่างที่ต้องใช้ไว้ในที่เดียว ไม่ต้องตั้งเซิร์ฟเวอร์เอง

| **Auto API** | สร้างช่องทางเชื่อมต่อให้อัตโนมัติ ประหยัดงานหลังบ้าน |

### Row Level Security (RLS) — ฟีเจอร์ที่สำคัญที่สุดสำหรับเรา

ตั้งกฎที่**ตัวฐานข้อมูล**ว่าใครเห็นแถวไหนได้:
- พนักงานเห็นคำเบิกของตัวเองเท่านั้น
- เจ้าของเห็นทุกคำเบิก
- **คนทั่วไปเห็นแค่ "รถว่างช่วงไหน" ไม่เห็นชื่อคนจอง**

ข้อสุดท้ายคือทางแก้จริงของปัญหาข้อมูลรั่ว — ตอนนี้แก้ที่หน้าบ้าน กันคนทั่วไปได้ แต่กันคนเปิด developer tools ไม่ได้
พอมี RLS ฐานข้อมูลจะ**ไม่ส่งข้อมูลนั้นมาตั้งแต่แรก**

### ราคา (ตรวจสอบ ก.ย. 2569)

| | ฟรี | Pro |
|---|---|---|
| ฐานข้อมูล | 500 MB | 8 GB |
| ไฟล์/รูป | 1 GB | 100 GB |
| สำรองข้อมูลอัตโนมัติ | ❌ ไม่มี | ✅ รายวัน |
| พักตัวเมื่อไม่มีคนใช้ 1 สัปดาห์ | ใช่ | ไม่ |
| ราคา | 0 | $25/เดือน (~฿850) |

500 MB เก็บข้อมูลตัวหนังสือได้หลายหมื่นรายการ · 1 GB เก็บรูปได้ ~3,000-5,000 รูป

**แนะนำ:** เริ่มฟรี พอเริ่มเก็บหลักฐานจริงจังค่อยขึ้น Pro เพราะ**แพ็กฟรีไม่มีระบบสำรองข้อมูล**

## ส่วนที่ 9 — ที่เก็บข้อมูลในเบราว์เซอร์ (ที่ใช้อยู่ตอนนี้)

| | localStorage | IndexedDB | ฐานข้อมูลจริง |
|---|---|---|---|
| ขนาด | ~5 MB | หลายร้อย MB | ไม่จำกัด |
| เก็บงานที่เอกสารครบ | 3-5 งาน | หลายร้อยงาน | ไม่จำกัด |

| พนักงานเห็นข้อมูลเดียวกัน | ไม่ | ไม่ | **เห็น** |

### กฎ 7 วันของ Safari คืออะไร

Apple ลบข้อมูลที่เว็บเก็บไว้ในเครื่อง ถ้าผู้ใช้ไม่เข้าเว็บนั้นเกิน 7 วัน
(เริ่มตั้งแต่ iOS 13.4 · ครอบคลุม localStorage, IndexedDB, SessionStorage)

**ทำไม:** ป้องกันเว็บโฆษณาแอบฝังรหัสตามรอยผู้ใช้ — เว็บสุจริตโดนผลข้างเคียงไปด้วย

**นับยังไง:** นับ 7 วันที่ไม่ได้เข้าใช้ ไม่ใช่นับถอยหลังตายตัว — เข้าใช้ครั้งนึงตัวนับรีเซ็ต

| สถานการณ์ | ผล |
|---|---|
| เปิดใช้ทุกวัน | ไม่หาย |
| ปิดร้านไปเที่ยว 10 วัน | **หายหมด** |
| Chrome/Edge บนคอม | ไม่มีกฎนี้ |

**ตัวเว็บไม่หาย ลิงก์ยังเปิดได้ แต่ข้อมูลที่กรอกหาย**

## ภาคผนวก — ศัพท์ที่จะได้ยินบ่อย

| ศัพท์ | แปลว่า |
|---|---|
| **Deploy** | เอาโค้ดขึ้นใช้งานจริง |
| **Build** | แปลงโค้ดให้เบราว์เซอร์อ่านได้ |
| **API** | ช่องทางให้ 2 ระบบคุยกัน |
| **Endpoint** | ที่อยู่เฉพาะของ API แต่ละอัน |
| **Migration** | คำสั่งเปลี่ยนโครงสร้างฐานข้อมูล |
| **Schema** | พิมพ์เขียวโครงสร้างฐานข้อมูล |
| **Environment variable** | ค่าลับที่เก็บนอกโค้ด เช่น รหัสฐานข้อมูล |
| **CORS** | กฎว่าเว็บไหนเรียก API ไหนได้ |
| **Cache** | ที่พักข้อมูลชั่วคราวให้โหลดเร็วขึ้น |
| **Responsive** | หน้าจอปรับตามขนาดอุปกรณ์ |
| **Regression** | ของที่เคยใช้ได้แล้วพังเพราะแก้อย่างอื่น |
| **Hotfix** | แก้ด่วนบนระบบจริง |
| **Rollback** | ย้อนกลับไปเวอร์ชันก่อน |
