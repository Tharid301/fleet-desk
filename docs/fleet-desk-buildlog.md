## 1. สถานะปัจจุบัน

### แท็บในระบบ (ฝั่งบริษัท)
| แท็บ | หน้าที่ | สิทธิ์ |
|---|---|---|
| กองรถ | ข้อมูลรถ สถานะ ค่าเช่า ค่ามัดจำแยกรายคัน | เจ้าของ/พนักงาน แก้ได้ · นักบัญชีดูอย่างเดียว |
| คิวงาน | ปฏิทิน 2 มุมมอง: รายการ (agenda) + ตารางรวม (Gantt) | เจ้าของ/พนักงาน |
| งานเช่า | คำขอจอง → ยืนยัน → ส่งมอบ → ปิดงาน | เจ้าของ/พนักงาน แก้ได้ |
| ประวัติ | งานที่ปิดจบ/ยกเลิก + filter + export ข้อมูลดิบ | ทุก role |
| บัญชี | เงินสด/ค้างรับ · ภาพรวม · รายเดือน · รายปี · พาร์ทเนอร์ | เจ้าของ/นักบัญชี |

### ฝั่งลูกค้า (ไม่ต้องล็อกอิน)
เช็ครถว่างรายวัน → เลือกช่วงวัน-เวลา → เห็นราคาคำนวณสด → แนบตั๋วเดินทาง → รับทราบเงื่อนไข → เห็นยอดมัดจำ+เลขบัญชี → ส่งคำขอ (สถานะ `pending` รอบริษัทยืนยัน)

## 2. กฎธุรกิจที่ตกลงแล้ว (อย่าแก้โดยไม่ได้สั่ง)

### การคิดค่าเช่า
1. ไม่ถึง 24 ชม. = คิด 1 วันเต็ม
2. เกิน 1 วัน: เศษเกิน 3 ชม. → ปัดขึ้นเป็น 1 วันเต็ม
3. เกิน 1 วัน: เศษไม่เกิน 3 ชม. → คิดเป็นรายชั่วโมง (เศษนาที <30 ปัดลง, ≥30 ปัดขึ้น)

**เทสต์ที่ผ่านแล้ว 5/5:**
| รับ | คืน | ผลลัพธ์ |
|---|---|---|
| 8 ส.ค. 09:00 | 10 ส.ค. 11:00 | 2 วัน 2 ชม |
| 8 ส.ค. 09:00 | 10 ส.ค. 07:00 | 2 วัน |
| 8 ส.ค. 09:00 | 8 ส.ค. 18:00 | 1 วัน |
| 8 ส.ค. 09:00 | 9 ส.ค. 06:00 | 1 วัน |
| 8 ส.ค. 07:00 | 9 ส.ค. 12:00 | 2 วัน |

- คืนช้า → คิดตามเวลาคืนจริง (`calcActualBookingTotal`) · คืนเร็ว → ยึดตามที่จอง ไม่ลดราคา

### การเงิน
- **เงิน 3 ก้อน:** เงินโอนจอง (ล็อคคิว) → ยอดวันรับรถ → มัดจำค้ำประกัน (คืนตอนคืนรถ)
- **ค่ามัดจำแยกรายคัน** ตั้งที่แท็บกองรถ ดึงไปใช้อัตโนมัติ
- **รถพาร์ทเนอร์:** รายได้ของเพจนับเฉพาะ % คอมมิชชั่น ไม่ใช่ยอดเต็ม · หัก ณ ที่จ่าย + ค่าใช้จ่ายรถ ก่อนจ่ายคืนพาร์ทเนอร์
- **เงินมัดจำที่ริบ = รายได้ที่ต้องแสดงในภาษี** แยกบรรทัด "รายได้อื่น" เพื่อดูภายในได้ แต่รวมในยอดที่ยื่น (ไม่ทำบัญชี 2 เล่ม)
- **เงินสด ≠ กำไร** — ค่างวดรถออกเต็มจำนวนแต่ลงบัญชีแค่ดอกเบี้ย · ค่าเสื่อมเป็นรายจ่ายแต่ไม่มีเงินออก · มัดจำค้ำประกันเป็นหนี้สินไม่ใช่รายได้

### การปิดงาน
ปิดได้ต่อเมื่อครบ **4 เอกสาร**: สลิปโอนจอง + สัญญาที่เซ็น + รูปส่งมอบรถ + สลิปคืนมัดจำ
งานที่ปิด/ยกเลิกแล้ว = อ่านอย่างเดียว ย้ายไปแท็บประวัติอัตโนมัติ

## 6. หลักการทำงานที่ใช้ตลอดโปรเจกต์

- **แก้แบบต่อยอด ไม่รื้อใหม่** — ไฟล์เดียว 2,400+ บรรทัด แก้เฉพาะจุด
- **ตรวจ syntax ทุกครั้งก่อนส่ง** ด้วย esbuild — จับบั๊กได้หลายครั้ง (JSX fragment ไม่ปิด, ลบ function declaration โดยไม่ตั้งใจ, style ซ้ำ)
- **ทดสอบ logic การเงิน/วันที่ด้วยข้อมูลจริง** ไม่ใช่แค่ compile ผ่าน — จับบั๊ก timezone และยืนยันสูตรคิดเงินได้
- **อย่าเดาสาเหตุบั๊ก** — บั๊กเลื่อนหน้าจอเสียเวลา 3 รอบเพราะเดาโดยไม่ไปดูโครงสร้างจริง

## 7. บันทึกรายรอบ (Interaction & Decision Log)

> เริ่มบันทึกตั้งแต่ 16 ก.ย. 2569 ตามที่ผู้ใช้สั่ง — ทุกคำสั่งและทุกการตัดสินใจ

### รอบที่ 1 — เพิ่มเงินสด/ค้างรับ
**คำสั่ง:** "do as recommended and save log"

**ทำ:**
- เพิ่มแท็บย่อย "เงินสด/ค้างรับ" ในแท็บบัญชี ตั้งเป็นหน้าแรก
- เพิ่ม `computeCashFlow()` แยกจาก `computePnL()`

**การตัดสินใจสำคัญ:**
| ตัดสินใจ | เหตุผล |
|---|---|
| แยกเงินสดออกจากกำไรเป็นคนละฟังก์ชัน | ค่างวดรถออกเต็มจำนวนแต่ลงบัญชีแค่ดอกเบี้ย · ค่าเสื่อมเป็นรายจ่ายแต่ไม่มีเงินออก → ตัวเลขต่างกันโดยธรรมชาติ ถ้ารวมกันจะทำให้เข้าใจผิด |
| แสดงมัดจำค้ำประกันเป็นก้อนแยก ไม่รวมในรายได้ | เป็นหนี้สินที่ต้องคืนลูกค้า ถ้านับเป็นกำไรจะหลงคิดว่ามีเงินมากกว่าจริง |
| ตั้งเงินสดเป็นหน้าแรกแทนภาพรวม | เป็นตัวเลขที่ใช้ตัดสินใจรายวันมากกว่ากำไรทางบัญชี |

**ทดสอบ:** รันสูตรกับข้อมูลจำลอง 3 เคส (จ่ายครบ/จ่ายบางส่วน/ยกเลิกริบมัดจำ) ตรวจ 12 ค่า ตรงทั้งหมด จุดสำคัญคือค่างวดออก 4,800 (เงินสด) ไม่ใช่ 1,200 (ดอกเบี้ย)

**พบปัญหา:** ยังไม่เคยทำ log เลยตลอดโปรเจกต์ และ `fleet-db-schema.md` ค้างอยู่ที่ฉบับ 1 ส.ค. ไม่ตรงกับโค้ด → สร้างไฟล์นี้ขึ้นมา

### รอบที่ 2 — จุดคุ้มทุน + เตือนเอกสารหมดอายุ + ย่อ EBITDA
**คำสั่ง:** "1.fleet-db-schema.md คือไฟล์ไว้ทำอะไร 2.ทำต่อจากที่ค้าง 3.หลังจากนี้ให้บันทึก log ทุก interaction & decision"

**ทำ:**
1. **จุดคุ้มทุนต่อคัน** (`computeBreakeven`) — แสดงในแผงรายละเอียดรถ บอกว่าคันนี้ต้องปล่อยเช่ากี่วัน/เดือนถึงคุ้ม พร้อมแถบความคืบหน้าเทียบกับที่ปล่อยจริง
2. **เตือนเอกสารหมดอายุ** (`getExpiryAlerts`) — แบนเนอร์บนแท็บกองรถ เตือนล่วงหน้า 30 วัน แยกสีระหว่าง "ใกล้หมด" (เหลือง) กับ "หมดแล้ว" (แดง) + เพิ่มช่องกรอกวันหมดอายุในฟอร์มรถ
3. **ย่อ EBITDA/EBIT/EBT** ไว้ใต้ปุ่ม "ดูรายละเอียดแบบนักบัญชี" — หน้าหลักเหลือ รายได้ → หักค่าใช้จ่าย → กำไรสุทธิ

**การตัดสินใจสำคัญ:**
| ตัดสินใจ | เหตุผล |
|---|---|
| จุดคุ้มทุนใช้ค่างวด**เต็มจำนวน** ไม่ใช่แค่ดอกเบี้ย | เจ้าของต้องหาเงินสดมาจ่ายทั้งก้อนจริง คำถามคือ "ต้องปล่อยกี่วันถึงไม่ต้องควักเนื้อ" |
| รวมค่าเสื่อมในจุดคุ้มทุนด้วย | ถ้าไม่รวม จะดูเหมือนคุ้มทั้งที่จริงกำลังกินทุนรถตัวเอง |
| หักค่าน้ำมัน/ล้างออกจากค่าเช่าต่อวัน | ค่าใช้จ่ายพวกนี้โตตามการใช้งาน ไม่ใช่กำไรเต็มเม็ด |
| เตือนล่วงหน้า 30 วัน | พอให้เดินเรื่องต่อประกัน/ภาษีทัน แต่ไม่เตือนเร็วเกินจนคนชินแล้วไม่สนใจ |
| เอกสารหมดอายุ = ขึ้นเตือนสีแดง "ห้ามนำรถออกให้เช่า" | ขับรถที่ พ.ร.บ./ภาษีขาด ผิดกฎหมายและประกันไม่คุ้มครองถ้าเกิดอุบัติเหตุ เป็นความเสี่ยงที่แรงพอจะเตือนแบบเข้ม |

**ทดสอบ:**
- จุดคุ้มทุน Honda City: ต้องครอบคลุม 15,600/เดือน (ค่างวด 4,800 + ประกัน 850 + GPS 300 + เสื่อม 9,650) ÷ กำไรต่อวัน 1,647 = **10 วัน/เดือน** ✓
- MG4 (ไม่มีค่างวด): **14 วัน/เดือน** — สูงกว่าเพราะราคารถแพงกว่าแต่ค่าเช่าถูกกว่า สมเหตุสมผล ✓
- เตือนหมดอายุ: ทะเบียน 2ขค (หมดแล้ว 8 วัน) และ 1กข (เหลือ 15 วัน) ขึ้นเตือน ส่วน 1กท (ปีหน้า) ไม่ขึ้น ✓

**หมายเหตุ:** เผลอทิ้งฟังก์ชันเปล่า `computeBreakevenUnused()` ไว้ตอนแก้ ตรวจเจอและลบออกทันที

### รอบที่ 3 — ปรึกษาเรื่อง deployment (ไม่มีการแก้โค้ด)
**คำสั่ง:** ปรึกษาว่าทำเป็นเว็บต่อจะง่ายมั้ย · กังวลเรื่องต้องซื้อ domain มั้ย · ต้องมี data server เองมั้ย

**ประเด็นที่ต้องแก้ความเข้าใจ:**
- ผู้ใช้เข้าใจว่าต้อง "ทำแอปเสร็จก่อนแล้วค่อยแปลงเป็นเว็บ" → **ความจริงคือ prototype เป็นเว็บอยู่แล้ว** (React รันในเบราว์เซอร์) ไม่มีขั้นตอนแปลง
- ผู้ใช้เข้าใจว่าต้องมีเซิร์ฟเวอร์เอง → **ไม่ต้อง** ใช้ managed service (Supabase) ที่ดูแล DB + storage + auth + backup ให้

**ข้อสรุปที่ให้ไป (เช็คราคาจากเว็บ ณ ก.ย. 2569):**
| รายการ | ราคา |
|---|---|
| Domain .com | ~฿500/ปี (Cloudflare/Namecheap) |
| Vercel (โฮสต์หน้าเว็บ) | ฟรี เพียงพอสำหรับขนาดนี้ |
| Supabase Free | 500MB DB · 1GB ไฟล์ · **ไม่มี backup** · พักโปรเจกต์ถ้าไม่มีทราฟฟิก 7 วัน |
| Supabase Pro | $25/เดือน (~฿850) · 8GB DB · 100GB ไฟล์ · backup รายวัน |
| **รวมใช้งานจริง** | **~฿900/เดือน** |

**คำแนะนำ:** ข้ามแพ็กฟรี ไป Pro ตั้งแต่วันแรกที่ใช้จริง
- แพ็กฟรีไม่มี backup แต่ระบบเก็บสัญญาที่เซ็น/สลิปโอนเงิน = หลักฐานทางกฎหมาย หายไม่ได้
- คำนวณพื้นที่: 1 งาน ~5 รูป ~2.5MB (หลังบีบอัด) · 100 งาน/เดือน = 250MB/เดือน → 1GB ฟรีเต็มใน ~4 เดือน

**เตือนเรื่อง PDPA:** ระบบเก็บบัตรประชาชน/ใบขับขี่/เบอร์โทร เข้าข่าย พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล ต้องมีหน้าขอความยินยอม + แจ้งวัตถุประสงค์/ระยะเวลาเก็บ + รองรับคำขอลบข้อมูล → **แนะนำให้ปรึกษาผู้เชี่ยวชาญกฎหมายก่อนเปิดใช้จริง** (ช่วยออกแบบหน้าจอได้ แต่ข้อความทางกฎหมายไม่ควรเขียนเอง)

**ย้ำขอบเขตงานที่เหลือ:** งานก้อนใหญ่ไม่ใช่การ "แปลงเป็นเว็บ" แต่คือหลังบ้าน — ต่อ DB จริง, auth จริง, อัปโหลดไฟล์ขึ้นคลาวด์, และ **ล็อกกันจองซ้ำที่ระดับฐานข้อมูล** (ทำที่ frontend อย่างเดียวไม่ได้)

### รอบที่ 4 — ทำ Responsive สำหรับจอคอมพิวเตอร์
**คำสั่ง:** ส่งภาพระบบจองรถขององค์กร (sidebar + ตาราง) · ถามว่าถ้าเปลี่ยน/เพิ่ม design แบบนี้ยากมั้ย · อยากได้ทั้ง 2 แบบ → หลังประเมินแล้วเลือก **"Responsive ชุดเดียว"**

**ประเมินที่ให้ไปก่อนตัดสินใจ:**
- เตือนว่าทำ 2 design แยก = ดูแล 2 เท่า ทุกฟีเจอร์/บั๊กต้องทำ 2 รอบ ซึ่งเสี่ยงเพราะโปรเจกต์นี้เจอบั๊กมาเยอะ
- เสนอ responsive แทน: โค้ดชุดเดียว เปลี่ยนหน้าตาตามขนาดจอ → ยังเปรียบเทียบได้โดยย่อ-ขยายหน้าต่าง
- ติงจุดอ่อนในภาพอ้างอิง: มี scrollbar แนวนอนทำให้คอลัมน์สุดท้ายถูกตัด → รับโครงสร้างมา แต่เลี่ยงจุดนี้

**ทำ:**
| ส่วน | มือถือ (<1024px) | คอม (≥1024px) |
|---|---|---|
| โครงหน้าจอ | แท็บด้านบน (เดิม) | **Sidebar ซ้าย** + ผู้ใช้/เมนู/ปุ่มระบบ + หัวข้อหน้าด้านบน |
| กองรถ | การ์ด 2-3 คอลัมน์ | การ์ด **4-5 คอลัมน์** |
| งานเช่า | การ์ดแนวตั้ง | **ตาราง 7 คอลัมน์** (ลูกค้า/เบอร์/รถ/รับ/คืน/สถานะ/เอกสาร) |
| ประวัติ | การ์ดแนวตั้ง | **ตาราง 7 คอลัมน์** + นับเอกสาร n/5 |
| คิวงาน | 7 วัน | **14 วัน** ต่อหน้าจอ |
| Popup | เต็มความกว้าง | กว้างขึ้น (max-w-2xl) |

**การตัดสินใจสำคัญ:**
| ตัดสินใจ | เหตุผล |
|---|---|
| ใช้ breakpoint `lg` (1024px) แบ่งมือถือ/คอม | แท็บเล็ตแนวตั้งยังได้เลย์เอาต์มือถือซึ่งเหมาะกว่า sidebar บนจอแคบ |
| กองรถใช้การ์ดไม่ใช่ตาราง | รถต้องดูรูป+สี ตารางแสดงภาพไม่ดี ส่วนงานเช่า/ประวัติเป็นข้อมูลตัวอักษร → ตารางเหมาะกว่า |
| เลือกเฉพาะคอลัมน์สำคัญ ไม่ยัดทุกฟิลด์ | เลี่ยงปัญหา scroll แนวนอนแบบในภาพอ้างอิง กดที่แถวเพื่อดูรายละเอียดเต็มแทน |
| ปฏิทินคอมแสดง 14 วัน + ปุ่มเลื่อนขยับ 14 วันตาม | ใช้พื้นที่จอกว้างให้เป็นประโยชน์ และปุ่มเลื่อนต้องสอดคล้องกับจำนวนวันที่เห็น ไม่งั้นข้ามวันหรือซ้ำ |

**ยังไม่ได้ทำ:** ฟอร์ม 2 คอลัมน์บนจอคอม (แบบภาพที่ 2) — popup กว้างขึ้นแล้วแต่ฟิลด์ยังเรียงคอลัมน์เดียว ต้องจัดกลุ่มฟิลด์ใหม่ทีละฟอร์ม

**หมายเหตุ:** รอบก่อนหน้าส่ง prop `wide` ไปแล้วแต่ยังไม่มี component ไหนรับ (ไม่มีผล) รอบนี้ต่อให้ครบ 4 component แล้ว

### รอบที่ 5 — แก้ปัญหาเลย์เอาต์คอมไม่แสดง + เพิ่มปุ่มสลับเอง
**คำสั่ง:** "เปิดในคอมหน้าจอ 14 นิ้วแล้วก็ยังเห็นเป็นแบบมือถือ"

**สาเหตุ:** ใช้ CSS breakpoint `lg` (1024px) ตัดสินเลย์เอาต์ แต่แอปรันอยู่ในแผง preview / iframe ที่กว้างไม่เท่าหน้าจอจริง — จอ 14" (~1440px) แบ่งครึ่งกับหน้าแชทเหลือ ~600-700px จึงไม่ถึงเกณฑ์ **CSS breakpoint วัดความกว้างของกรอบที่แอปอยู่ ไม่ใช่ความกว้างจอ**

**แก้:**
- เปลี่ยนจาก CSS class (`hidden lg:flex` / `lg:hidden`) เป็น **วัดความกว้างด้วย JS** (`window.innerWidth` + resize listener) แล้วเลือก render ทีละชุด
- เพิ่ม **ปุ่มสลับเลย์เอาต์เอง** ("ดูแบบคอม" / "ดูแบบมือถือ") อยู่ใน sidebar (ฝั่งคอม) และใต้หัวข้อ (ฝั่งมือถือ) — override การตรวจอัตโนมัติได้
- ปุ่มแสดงความกว้างปัจจุบันใน tooltip เพื่อให้เห็นว่าระบบวัดได้เท่าไหร่

**การตัดสินใจ:**
| ตัดสินใจ | เหตุผล |
|---|---|
| ไม่ลด breakpoint ลงต่ำกว่า 1024px | sidebar 240px + ตาราง 7 คอลัมน์ ต้องการพื้นที่จริง ถ้าลดเกณฑ์จะได้ตารางที่บีบจนอ่านไม่ออก |
| ใช้ JS วัดแทน CSS ล้วน | ต้องการให้ปุ่ม override ทำงานได้ ซึ่ง CSS media query ทำไม่ได้ |
| คงปุ่มสลับไว้ถาวร ไม่ใช่แค่ debug | ตรงกับที่ผู้ใช้อยากเปรียบเทียบ 2 แบบก่อนตัดสินใจเลือกใช้จริง |

### รอบที่ 6 — แยกทางเข้าลูกค้า/พนักงาน + ปุ่มสลับเลย์เอาต์ฝั่งลูกค้า
**คำสั่ง:** 1) ถามว่าควรแยก web link ของลูกค้าออกมั้ย เพื่อไม่ให้ลูกค้าเห็นบัญชีพนักงาน 2) ฝั่งลูกค้ายังไม่มีปุ่มสลับมุมมองคอม

**คำตอบข้อ 1 (สถาปัตยกรรม):** ควรแยก — โค้ดชุดเดียว แต่แยกทางเข้า
| URL | ใคร | เห็นอะไร |
|---|---|---|
| `ชื่อเว็บ.com` | ลูกค้า | เช็ครถว่าง + จอง เท่านั้น |
| `ชื่อเว็บ.com/admin` | พนักงาน | login → ระบบจัดการ |

**แย้งผู้ใช้เรื่องการจองแทนลูกค้าที่โทรมา:** ไม่ควรให้พนักงานไปจองผ่านหน้าลูกค้า ควรใช้ปุ่ม "จองใหม่" ในแท็บงานเช่าแทน เพราะ (1) หน้าลูกค้าบังคับแนบตั๋ว + สถานะเป็น pending ต้องยืนยันซ้ำ เสียเวลา (2) หน้าพนักงานตั้งมัดจำเองได้ ยืนยันได้ทันที (3) ตรงกับกฎที่ตกลงไว้ว่า "ลูกค้าไม่มีตั๋ว → บริษัทจองให้"

**ทำ:**
- ฝั่งลูกค้า: เพิ่มปุ่มสลับเลย์เอาต์ + เลย์เอาต์คอมแสดงรถเป็นกริด 2-3 คอลัมน์ (เดิม max-w-md ตายตัว)
- หน้า login: **ซ่อนรายชื่อบัญชีทดสอบเป็นค่าเริ่มต้น** ต้องกด "แสดงบัญชีทดสอบ" ก่อน + เพิ่มกล่องอธิบายโครงสร้าง 2 URL + เปลี่ยนหัวข้อเป็น "สำหรับเจ้าหน้าที่"
- เปลี่ยนป้ายปุ่มเป็น "เปิดหน้าลูกค้า (จำลองลิงก์ ชื่อเว็บ.com)" ให้สื่อว่าเป็นคนละลิงก์กัน

**การตัดสินใจ:**
| ตัดสินใจ | เหตุผล |
|---|---|
| ซ่อนบัญชีทดสอบแทนที่จะลบ | ยังต้องใช้ทดสอบ role ต่างๆ แต่ไม่ควรโชว์เป็นค่าเริ่มต้นเพราะขัดกับสิ่งที่ผู้ใช้กังวล |
| ไม่แยกไฟล์ 2 ชุด | prototype ไฟล์เดียวจำลองได้พอ · ของจริงแยกด้วย routing ไม่ใช่แยก codebase |

### รอบที่ 7 — เพิ่มหน้าแรกเว็บบริษัท (Homepage)
**คำสั่ง:** 1) ยืนยันตรงกันเรื่องจองแทนลูกค้า (แค่ยกเคสหน้างาน) 2) อยากให้หน้าลูกค้ามี homepage แบบเว็บบริษัททั่วไปก่อนเข้าหน้าจอง · design ยังไม่มี ให้ทำ demo ไว้ก่อน

**ทำ — เส้นทางเข้าใหม่:**
```
หน้าแรก (HomePage)  ←── ค่าเริ่มต้นเมื่อเปิดเว็บ
   ├─ ปุ่ม "เช็ครถว่าง & จองเลย" → หน้าจองของลูกค้า → กลับหน้าแรกได้
   └─ ลิงก์เล็ก "สำหรับเจ้าหน้าที่" (ใน footer) → หน้า login → ระบบจัดการ
                                                      └─ ออกจากระบบ → กลับหน้าแรก
```
ตรงกับโครงสร้าง URL จริง: `ชื่อเว็บ.com` = หน้าแรก · `ชื่อเว็บ.com/admin` = เจ้าหน้าที่

**โครงหน้าแรก (placeholder design):**
1. แถบบนติดหน้าจอ + ปุ่มจองรถ + ปุ่มสลับมุมมองคอม/มือถือ
2. Hero — ชื่อร้าน, จุดขาย, จำนวนรถว่าง (ดึงจากข้อมูลจริง), ราคาเริ่มต้น (คำนวณจากรถถูกสุดจริง), ปุ่ม CTA + เบอร์โทรกดโทรได้
3. จุดเด่น 4 ข้อ (ประกันชั้น 1 / รับ-ส่งถึงที่ / ราคาชัดเจน / รถสะอาด)
4. รถที่ว่างตอนนี้ — ดึงจากกองรถจริง แสดงราคา/ประเภท/สี
5. ขั้นตอนการเช่า 4 ขั้น (ตรงกับ flow จริงในระบบ)
6. กล่อง CTA + ช่องทางติดต่อ (โทร/LINE/อีเมล)
7. Footer + ลิงก์เจ้าหน้าที่

**การตัดสินใจ:**
| ตัดสินใจ | เหตุผล |
|---|---|
| ดึงข้อมูลจริงมาแสดง (จำนวนรถว่าง, ราคาต่ำสุด, รายการรถ) ไม่ใช่ข้อความตายตัว | หน้าแรกจะอัปเดตเองตามกองรถ ไม่ต้องมาแก้ข้อความทุกครั้งที่เพิ่ม/ลดรถ |
| ลิงก์เจ้าหน้าที่อยู่ footer ตัวเล็กสีจาง | เป็นมาตรฐานเว็บบริษัท — ลูกค้าไม่สะดุดตา แต่พนักงานหาเจอ |
| ออกจากระบบ → กลับหน้าแรก ไม่ใช่หน้า login | ให้เหมือนเว็บจริงที่ logout แล้วกลับหน้าสาธารณะ |
| แยกข้อมูลบริษัทเป็นค่าคงที่ `COMPANY` | เปลี่ยนชื่อร้าน/เบอร์/LINE ได้ที่เดียว ตอนทำจริงย้ายไปตาราง settings ได้ |
| ทำ design เรียบๆ ใช้ชุดสีเดิม | ผู้ใช้แจ้งว่าจะให้ design ทีหลัง — ทำโครงไว้ให้เห็นภาพ เปลี่ยนหน้าตาภายหลังได้โดยไม่กระทบ logic |

**หมายเหตุ:** ข้อมูลบริษัทในหน้าแรก (ชื่อ "ไทยรถเช่า", เบอร์, LINE, อีเมล) เป็นตัวอย่างสมมติ ต้องเปลี่ยนเป็นของจริงก่อนใช้งาน

### รอบที่ 8 — เอาขึ้นเว็บจริง + ทำให้ข้อมูลไม่หายเมื่อรีเฟรช
**คำสั่ง:** ถามว่าไฟล์ prototype ใช้จริงไม่ได้ใช่มั้ย · เอาขึ้นเว็บได้มั้ย · แก้ในนั้นต่อได้มั้ย · โดเมนเริ่มฟรีแล้วซื้อทีหลังได้มั้ย → เลือกทำข้อ 1 (ทำให้ข้อมูลไม่หายก่อน)

**ตอบคำถาม:**
- ไฟล์ `.jsx` เป็นซอร์สโค้ด เปิดในเบราว์เซอร์ตรงๆ ไม่ได้ ต้อง build ก่อน — ถูกต้อง
- โดเมน: เริ่มฟรีแล้วซื้อทีหลังได้ โดเมนกับตัวเว็บแยกกันคนละส่วน ย้ายได้ไม่ต้องสร้างใหม่

**ทำ — build + publish เป็นเว็บจริง:**
- `npm install react react-dom recharts lucide-react xlsx` → bundle ด้วย esbuild (iife, minify) → ฝังใน HTML ไฟล์เดียว + Tailwind CDN
- ผลลัพธ์ ~1.06 MB · เผยแพร่ที่ https://claude.ai/artifact/PUKkHT7jUUNHUN44rQnB9R (แก้แล้ว publish ทับลิงก์เดิมได้)

**ทำ — ระบบจำข้อมูล (localStorage):**
- บันทึกอัตโนมัติทุกครั้งที่ข้อมูลเปลี่ยน: `accounts, cars, overhead, scheduleEvents, bookings, termsText, bankInfo`
- แสดงสถานะ "บันทึกแล้ว · X KB" + ปุ่มล้างข้อมูล (กด 2 ครั้งยืนยัน) ทั้งฝั่งคอมและมือถือ
- ตรวจจับพื้นที่เต็ม (QuotaExceededError) แล้วแจ้งเตือนแทนที่จะเงียบ

**ปัญหาที่ต้องแก้ไปพร้อมกัน — พื้นที่เก็บ:**
localStorage มีประมาณ 5MB แต่รูปถ่ายมือถือใบเดียว 3-5MB → แนบรูปเดียวก็เต็ม
**แก้:** เพิ่มการย่อรูปด้วย canvas ก่อนเก็บ (ย่อด้านยาวสุดเหลือ 1400px, JPEG คุณภาพ 0.7) → รูป 4MB เหลือ ~150-300KB เก็บได้ ~30 รูปแทนที่จะเป็น 1 รูป
- PDF ย่อไม่ได้ → จำกัดที่ 3MB พร้อมข้อความแนะนำให้สแกนความละเอียดต่ำลง
- เพิ่มสถานะ "กำลังย่อรูป..." ระหว่างประมวลผล

**บั๊กที่เจอระหว่างทำ (สำคัญ):**
วาง `useEffect` ของการบันทึกไว้**หลัง** `if (...) return` ซึ่งผิดกฎ Rules of Hooks ของ React → จะ crash ทันทีที่สลับหน้าจอ (เช่น กดเข้าหน้าลูกค้า) ตรวจเจอด้วยการไล่ดูลำดับบรรทัด แล้วย้ายขึ้นไปก่อน return ทั้งหมด + เขียนสคริปต์สแกนยืนยันว่าไม่เหลือ hook ไหนอยู่หลัง return อีก (ผลลัพธ์: 0)

**การตัดสินใจ:**
| ตัดสินใจ | เหตุผล |
|---|---|
| ย่อรูปเป็น JPEG 1400px แทนเก็บไฟล์เดิม | สลิป/สัญญาอ่านออกชัดที่ขนาดนี้ และทำให้เก็บได้จริงหลายสิบรูป |

### รอบที่ 9 — ระบบบันทึกรายจ่ายอื่น + แยกเงินถอนของเจ้าของ
**คำสั่ง:** ถามว่าเงินที่เอาออกไปใช้นอกเหนือจากค่าล้างรถ ฯลฯ เช่น งานเลี้ยงบริษัท หรือเจ้าของเอาไปใช้ส่วนตัว ต้องบันทึกยังไง เข้าใจว่าต้องแยกไว้

**หลักบัญชีที่อธิบายไป — 2 ประเภทนี้ต่างกันโดยสิ้นเชิง:**
| ประเภท | ลดกำไร? | หักภาษีได้? | ลดเงินสด? |
|---|---|---|---|
| **รายจ่ายบริษัท** (งานเลี้ยงพนักงาน, ค่าทำบัญชี, ของใช้สำนักงาน) | ✅ ใช่ | ✅ ได้ ถ้ามีใบเสร็จในชื่อบริษัท | ✅ ใช่ |
| **เจ้าของถอนไปใช้ส่วนตัว** | ❌ **ไม่** | ❌ **ไม่ได้** | ✅ ใช่ |

เหตุผลที่ต้องแยก: ถ้าบันทึกเงินถอนส่วนตัวเป็นรายจ่าย → กำไรจะดูต่ำกว่าความจริง (ตัดสินใจผิดว่าธุรกิจไม่ดี) และสรรพากรจะไม่ยอมรับ อาจโดนเรียกเก็บภาษีย้อนหลัง

**ทำ:**
- เพิ่มสมุดรายจ่าย `otherExpenses` + 8 หมวด โดยหมวด `owner_draw` ตั้งค่า `drawing: true` แยกออกจากหมวดอื่น
- `computePnL` นับเฉพาะรายจ่ายบริษัท (ไม่นับเงินถอน) · `computeCashFlow` นับทั้งสอง
- แท็บย่อยใหม่ "รายจ่ายอื่น" ในหน้าบัญชี: สรุปยอด 2 ก้อนแยกกัน + ฟอร์มบันทึก + แนบใบเสร็จ + รายการย้อนหลัง
- เตือนแบบ real-time ตอนเลือกหมวด ว่าเงินก้อนนี้จะลดกำไรหรือไม่
- เตือนรายการที่ยังไม่แนบใบเสร็จ ("อาจหักภาษีไม่ได้")
- แสดงบรรทัดแยกในงบกำไรขาดทุนและกระแสเงินสด

**ทดสอบ (สำคัญ — ต้องไม่ผิด):** งานเลี้ยง 3,000 + เจ้าของถอน 20,000
- กำไรลดลง **2,400** = 3,000 × (1 − ภาษี 20%) → เงินถอน 20,000 ไม่กระทบกำไรเลย ✅
- เงินสดลดลง **23,000** = ทั้งสองรายการ ✅

**การตัดสินใจ:**
| ตัดสินใจ | เหตุผล |
|---|---|
| ทำเป็นหมวดหมู่ตายตัว ไม่ให้พิมพ์เอง | กันบันทึกผิดประเภท ซึ่งเป็นความเสี่ยงทางภาษีจริง |
| เตือนตอนเลือกหมวด ไม่ใช่เตือนตอนท้าย | ผู้ใช้เห็นผลกระทบก่อนบันทึก ไม่ต้องมาแก้ทีหลัง |
| ให้แนบใบเสร็จได้ + เตือนถ้าไม่มี | ใบเสร็จคือเงื่อนไขหลักในการหักภาษี ระบบควรช่วยเตือนตั้งแต่ต้น |
| ไม่แนะนำวิธีจัดการภาษีเงินถอนเอง | เป็นเรื่องเฉพาะราย (นิติบุคคล/บุคคลธรรมดา ต่างกัน) ใส่ข้อความแนะนำให้ปรึกษาผู้ทำบัญชีแทน |

### รอบที่ 10 — ระบบเบิกเงิน + กระแสเงินสด 3 กลุ่ม + หมวดหมู่ครบทุกกรณี
**คำสั่ง:** ถามว่าหมวดอยู่ตรงไหน · เคสลงทุน (ซื้อรถ ปรับปรุงออฟฟิศ) และพนักงานเบิกเงิน ต้องบันทึกยังไง · อยากให้ cover ทุก possibility ของ cash flow · ส่งภาพฟอร์มเบิกเงินของ Honda มาเป็นแบบอ้างอิง

**คำตอบเชิงบัญชี — แบ่งกระแสเงินสดเป็น 3 กลุ่ม (นี่คือคำตอบของ "ทุก possibility"):**
| กลุ่ม | กระทบกำไร? | ตัวอย่าง |
|---|---|---|
| **ดำเนินงาน** | ✅ | ค่าเช่าเข้า, น้ำมัน, ล้างรถ, ซ่อม, เงินเดือน, งานเลี้ยง |
| **ลงทุน** | ❌ | **ซื้อรถ**, **ปรับปรุงออฟฟิศ**, ซื้ออุปกรณ์ถาวร, ขายรถออก |
| **จัดหาเงิน** | ❌ | รับเงินกู้, คืนเงินต้น, **เจ้าของเติมเงิน**, **เจ้าของถอน** |

**จุดสำคัญ:** ซื้อรถ 800,000 เงินออกจริงแต่**ไม่ใช่รายจ่าย** — รถเป็นทรัพย์สิน ทยอยเป็นรายจ่ายผ่านค่าเสื่อม ถ้าลงเป็นรายจ่ายทั้งก้อนจะขาดทุนยับทั้งที่ธุรกิจปกติ

**ทำ:**
1. **หมวดหมู่ 19 หมวด** ครอบคลุมทั้ง 3 กลุ่ม แต่ละหมวดมี `flow` + `dir` (เข้า/ออก) — เดิมฝังในโค้ด ตอนนี้เป็น state เก็บลง localStorage แล้ว
2. **ระบบเบิกเงิน (แท็บใหม่ "เบิกเงิน")** ทุก role เข้าได้:
   - ฟอร์มตามแบบที่ผู้ใช้ส่งมา: ผู้ขอเบิก (ดึงจาก login, แก้ไม่ได้) · วันที่ชำระเงิน · จำนวนเงิน (มีข้อความกำกับ "จำนวนเต็ม ไม่เกินใบเสร็จ") · หมายเหตุ · แนบเอกสาร 1.ใบเสร็จ (บังคับ) 2.เอกสารอื่น (ไม่บังคับ) — เพิ่มช่องผูกกับรถคันไหนเข้าไปด้วย
   - Flow: `รออนุมัติ → อนุมัติแล้ว → จ่ายคืนแล้ว` (หรือ `ไม่อนุมัติ` พร้อมเหตุผล)
   - เจ้าของเห็นแท็บย่อย "รออนุมัติ / รอจ่ายคืน" พร้อมยอดค้างจ่ายคืนรวม
3. **กระแสเงินสดแสดงแยก 3 กลุ่ม** พร้อมป้ายกำกับว่ากลุ่มไหนไม่กระทบกำไร

**หลักบัญชีของคำร้องเบิก (สำคัญ):**
- เป็น**รายจ่าย**ตอน **อนุมัติ** (มีใบเสร็จแล้ว = ต้นทุนเกิดแล้ว)
- ตัด**เงินสด**ตอน **จ่ายคืน**
- ช่วงคาบเกี่ยว = "ค้างจ่ายคืนพนักงาน" แสดงแยกให้เห็น

**ทดสอบ:** ใส่ครบทุกกรณี (งานเลี้ยง 3,000 / ถอนส่วนตัว 20,000 / ซื้อรถ 800,000 / เติมเงิน 500,000 / รายได้อื่น 1,500 / คำร้อง 3 สถานะ)
- กำไรเปลี่ยน 7,520 → 3,760 = ลดเฉพาะ (3,000 + 3,200 คำร้องอนุมัติ − 1,500 รายได้อื่น) × 0.8 ✅
- ซื้อรถ/ถอน/เติมเงิน **ไม่แตะกำไรเลย** ✅
- เงินสดขยับครบทุกรายการ ✅ · คำร้องที่ยังไม่อนุมัติไม่ถูกนับทั้งสองฝั่ง ✅

**บั๊กที่เจอระหว่างทำ:** ใช้ตัวแปร `oxSplit` ก่อนบรรทัดที่ประกาศ (temporal dead zone) → จะ crash ตอนเรียกใช้จริง คอมไพเลอร์จับไม่ได้ ตรวจเจอด้วยการไล่ลำดับบรรทัดเอง แล้วย้ายการประกาศขึ้นไปบนสุดของฟังก์ชัน

**ยังไม่ได้ทำ (ค้างไว้):** UI จัดการหมวดหมู่ (เพิ่ม-แก้-ลบเอง) และการเชื่อม "ซื้อรถ → สร้างรถในกองรถต่อทันที" — โครงสร้างข้อมูลรองรับแล้ว เหลือหน้าจอ

### รอบที่ 11 — แก้บั๊กหน้าบัญชี + ทศนิยม 2 ตำแหน่ง + แก้/ยกเลิกคำร้อง + ซื้อรถเชื่อมกองรถ
**คำสั่ง:** 1) หน้าบันทึกรายจ่ายเข้าไม่ได้ เป็นบั๊กหรือเปล่า 2) ซื้อรถเพิ่มตรงไหน 3) ควรใช้ทศนิยม 2 หลัก กลัวดอกเบี้ยเงินกู้เลขไม่ตรงตอนตรวจบัญชี 4) ส่งคำร้องแล้วควรแก้/ยกเลิกเองได้ก่อนอนุมัติ 5) ระบุวันที่+ผู้อนุมัติ เผื่ออนาคตมีหลายระดับ

**1. บั๊ก — เป็นบั๊กจริง และร้ายแรง**
รอบก่อนเปลี่ยนชื่อ `EXPENSE_CATEGORIES` → `DEFAULT_EXPENSE_CATEGORIES` และเปลี่ยนโครงสร้างจาก `drawing: bool` เป็น `flow` แต่ `ExpensePanel` ยังอ้างชื่อเดิม → **ReferenceError ทำให้ทั้งหน้าพัง** ทันทีที่กดเข้า
- คอมไพเลอร์จับไม่ได้ (ชื่อตัวแปรที่ไม่มีอยู่จริงเป็น runtime error)
- **บทเรียน:** การ refactor ที่เปลี่ยนชื่อ/โครงสร้าง ต้อง grep หาทุกจุดที่อ้างถึง ไม่ใช่แค่ดูว่า compile ผ่าน
- แก้โดยเขียน `ExpensePanel` ใหม่ทั้งหมดให้ใช้โครงสร้าง 3 กลุ่ม + ตรวจยืนยันว่าไม่เหลือชื่อเก่า (0 จุด)

**2. ซื้อรถ — ทำเสร็จแล้ว** บัญชี → รายจ่ายอื่น → เลือกหมวด "ซื้อรถเข้ากอง" → บันทึก → **ระบบเปิดหน้าเพิ่มรถให้ทันที พร้อมกรอกราคาซื้อไว้แล้ว** กรอกทะเบียน/รุ่นต่อได้เลย

**3. ทศนิยม 2 ตำแหน่ง — เปลี่ยนแล้ว**
เดิม `fmt()` ปัดเป็นจำนวนเต็ม → เปลี่ยนเป็นทศนิยม 2 ตำแหน่งเสมอ · แยก `fmtInt()` ไว้ใช้กับจำนวนนับ (วัน/คัน/%) ที่ไม่ควรมีทศนิยม · ช่องกรอกเงินรับ `step="0.01"`
เหตุผลตรงกับที่ผู้ใช้กังวล: ดอกเบี้ย/ค่าคอมมิชชั่น/ภาษี ถ้าปัดเศษทุกจุดจะสะสมจนยอดไม่ตรงตอนกระทบยอด

**4. แก้/ยกเลิกคำร้องเอง — ทำแล้ว**
- สถานะ `pending` + เป็นคำร้องของตัวเอง → แก้วันที่/จำนวนเงิน/หมายเหตุ หรือยกเลิกเองได้ (ยกเลิกต้องกดยืนยัน 2 ชั้น)
- พออนุมัติ/ไม่อนุมัติแล้ว → **ล็อกถาวร** แก้ไม่ได้ พร้อมข้อความอธิบายว่าถูกบันทึกเป็นหลักฐานแล้ว
- เพิ่มสถานะ `cancelled` แยกจาก `rejected` (ยกเลิกเอง ≠ ถูกปฏิเสธ)

**5. ประวัติการอนุมัติ — ทำแล้ว** แสดงเป็นไทม์ไลน์: ส่งคำร้องโดยใคร/เมื่อไหร่ → อนุมัติหรือไม่อนุมัติโดยใคร/เมื่อไหร่ → จ่ายคืนเมื่อไหร่ พร้อมหมายเหตุว่ารองรับการเพิ่มลำดับขั้นตามวงเงินในอนาคต

**เพิ่มเติม: จัดการหมวดหมู่เองได้แล้ว** — ปุ่ม "หมวดหมู่" ในหน้ารายจ่ายอื่น เพิ่ม/เปลี่ยนชื่อ/ลบหมวดได้ · หมวดมาตรฐานเปลี่ยนชื่อได้แต่ลบไม่ได้ (ระบบใช้อ้างอิงคำนวณ) · ตอนเพิ่มหมวดใหม่ต้องเลือกกลุ่มและทิศทาง ระบบจะบอกว่ากระทบกำไรหรือไม่

### รอบที่ 12 — ล็อกทศนิยม 2 ตำแหน่ง + แก้คำร้องได้ทุกช่อง + เวลายื่นคำร้อง + ตัวอย่างไฟล์ export

### รอบที่ 15 — แก้ปัญหาเปิดบนมือถือ/ไอแพดแล้วหน้าขาว
**คำสั่ง:** ส่งภาพหน้าจอ — หน้าขาวทั้งมือถือและไอแพด console ขึ้นเตือน `cdn.tailwindcss.com should not be used in production`

**วิเคราะห์:** หน้าขาวสนิท = React ไม่ mount เลย ไม่ใช่แค่สไตล์หาย (ถ้าแค่ CSS หาย เนื้อหาจะยังโผล่แบบไม่มีสไตล์ และพื้นหลังเข้มจาก inline style จะติด) → แปลว่า JS พังตั้งแต่ตอน parse หรือตอนรัน

**แก้ 3 ชั้น:**
1. **ลด JS target เป็น ES2019** (เดิม esbuild default = esnext) — Safari รุ่นเก่าเจอ syntax ES2020 แล้ว parse ไม่ผ่านทั้งไฟล์ ผลคือหน้าขาวโดยไม่มี error ชัดเจน
   - ลอง `es2016/safari12` ก่อนแต่ esbuild แปลง destructuring ไม่ได้ (307 errors) → ใช้ `es2019` ซึ่งยัง strip optional chaining/nullish ได้
   - ตรวจซ้ำแล้วพบว่า `?.` `??` ที่เหลือในไฟล์เป็น false positive ทั้งหมด (อยู่ในสตริง format ของ Excel และ ternary `1?.05:.1`) — **บทเรียน: grep หา syntax ในไฟล์ minified เชื่อไม่ได้ ต้องดู context**
2. **เลิกใช้ Tailwind CDN** — คอมไพล์ด้วย Tailwind CLI สแกนเฉพาะคลาสที่ใช้จริง ได้ไฟล์ 16 KB ฝังในหน้าเลย ตัด dependency ที่ต้องต่อเน็ตและอาจถูกบล็อก
3. **ใส่ตัวดักจับ error แสดงบนหน้าจอ** — `window.onerror` + `unhandledrejection` + timeout 6 วินาทีเช็คว่า React mount หรือยัง ถ้าพังจะโชว์ข้อความ error + userAgent ให้ถ่ายหน้าจอส่งมาได้ แทนที่จะเป็นหน้าขาวที่ไม่บอกอะไร

**เหตุผลที่ทำข้อ 3 ด้วย:** ยังไม่ยืนยัน 100% ว่าสาเหตุคือข้อ 1 — ถ้าแก้แล้วยังพัง ตัวดักจับจะบอกสาเหตุจริงทันที ไม่ต้องเดาต่ออีกรอบ

### รอบที่ 16 — เจอสาเหตุจริงของหน้าขาว + ปิดช่องโหว่การทดสอบ
**คำสั่ง:** ส่งภาพ — ตัวดักจับ error แสดง `Uncaught ReferenceError: CLEAN_BUFFER_HOURS is not defined` และเกิดบน laptop ด้วย

`CLEAN_BUFFER_HOURS` ถูกใช้ 3 จุด แต่**ไม่เคยถูกประกาศเลย** ทำให้ JS ตายตั้งแต่โหลด → หน้าขาวทุกเครื่อง ทุกเบราว์เซอร์

1. ประกาศ `const CLEAN_BUFFER_HOURS = 1;` ที่ module scope
2. เขียนสคริปต์สแกนหา identifier ที่ถูกใช้แต่ไม่ถูกประกาศทั้งไฟล์ → ยืนยันไม่เหลือจุดอื่น (`CURRENT_LABEL`, `DISPLAY_START/END` ประกาศอยู่ใน function scope ปกติ)

   - ผลรอบนี้: mount สำเร็จ · เข้าได้ทุกหน้า · **runtime errors = 0**
   - ต่อไปต้องรันตัวนี้ก่อน publish ทุกครั้ง ไม่ใช่แค่ esbuild ผ่านแล้วส่ง

**บทเรียนหลัก:** `esbuild ผ่าน` = ไวยากรณ์ถูก ไม่ได้แปลว่าโปรแกรมรันได้ ตัวแปรที่ไม่มีอยู่จริงเป็น runtime error ที่ compiler มองไม่เห็น ต้องมีขั้นตอนเรนเดอร์จริงเสมอ

**เหตุผลที่ตัดที่ต้นทางแทนที่จะแก้ string:** ถ้าแก้แค่ข้อความ วันหน้าถ้าผมหรือใครเพิ่มฟีเจอร์ในหน้าลูกค้าแล้วเผลอดึง note มาใช้อีก มันจะรั่วซ้ำ การตัดข้อมูลตั้งแต่ต้นทำให้**ข้อมูลที่ไม่ควรเห็นไม่มีอยู่ในขอบเขตนั้นเลย**

**เพิ่มเทสต์ถาวร `privacy-test.cjs`:** เปิดหน้าลูกค้าจริงด้วย jsdom แล้วค้นหาชื่อ/เบอร์โทรของลูกค้าทุกรายในข้อมูลตัวอย่าง (14 ค่า) ว่าโผล่บนหน้าจอหรือไม่ → ผลรอบนี้ **leaked = NONE**

**ข้อจำกัดที่ต้องรู้:** prototype นี้เก็บข้อมูลทั้งหมดไว้ในเบราว์เซอร์ คนที่เปิด developer tools ยังอ่านข้อมูลดิบได้อยู่ดี **การแยกข้อมูลจริงต้องทำที่ backend** — ตอนทำระบบจริง endpoint ฝั่งลูกค้าต้องคืนเฉพาะช่วงเวลาว่าง ห้ามคืนข้อมูลการจอง เพิ่มหมายเหตุนี้ไว้ใน schema แล้ว
